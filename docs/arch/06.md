## 6. 文件与函数大小

统计口径：物理行数（含空行与注释）。生成文件、协议样例、迁移 SQL、锁文件不计，但必须在 `tools/check-file-size/allowlist.json` 里登记路径模式与理由。

| 对象 | 建议上限 | 现行脚本阈值 |
| --- | --- | --- |
| 普通源文件（`.ts` / `.tsx` / `.py`） | 400 行 | **600 行** |
| 入口与装配文件（`main/index.ts`、`composition-root.ts`、`preload/index.ts`、`renderer/main.tsx`、`oi_worker/__main__.py`） | 100 行 | **150 行** |
| React 组件文件 | 250 行 | 400 行 |
| 测试文件 | 600 行 | 800 行 |
| 函数 / 方法 | 50 行 | **80 行**（ESLint `max-lines-per-function` / ruff `PLR0915` 等价配置） |
| 圈复杂度 | 10 | **15** |
| 函数参数 | 3 个 | 4 个（更多用对象参数） |

- **domain 纯函数的例外**（架构评审 P2-1）：`features/*/src/domain/**` 与 Python core（§2.3）里的纯函数不受函数 50 / 80 行的限制，只受文件上限与圈复杂度约束；按「一个不变量一个文件」拆分（例如 `integrity-check` 的每条检查一个文件），评审看一个文件承接几个不变量（RULES §5 第 2 条）。这是 ESLint / ruff 按路径的配置，不是 allowlist 豁免。adapters、application、UI 与入口仍受函数上限约束。
- 上表的数是现行脚本仍会拿来失败的阈值，不是本项目的机械设计约束。`check-file-size` 仍按普通源文件 600、入口 150、组件 400、测试 800 失败。`check-pr-size` 仍按非生成增删合计 600 失败，除非提交说明或 `PR_BODY` 已有 `G12:`。这两处脚本、全仓阈值和分支保护，本条不改。失败不能记成通过。
- 功能归到对应的模块和文件。一个文件只承接一种职责。不同功能不堆进同一个文件。依赖只沿 §5，界面只经 seam 调用 core。
- 总 diff、单文件行数、职责是否耦合，分开审查。合理规模和为什么这样分，写在 PR 里。用户举过的几千行或一万行只是例子，不是额度。不为每个小函数单独建文件。拆开后仍共享一大块可变状态，不算解耦。不压缩格式，不删测试，不用没有语义的拆分去迎合行数。
- 超过建议上限时，PR 描述写明为什么这样分。豁免进 allowlist 仍只能经过 ADR，并写**到期里程碑**；到期未处理，现行脚本仍失败。
- 行数落在阈值里不等于职责单一。评审仍按 RULES.md 检查职责数量与依赖扇出。
