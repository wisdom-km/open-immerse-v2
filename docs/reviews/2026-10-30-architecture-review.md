# Open Immerse v2 架构评审（2026-10-30）

评审对象：`main@cfcafdd`（PR #3 合入的规格基线）。
只读范围：`PRD.md`、`ARCHITECTURE.md`、`RULES.md`、`LICENSE`、`README.md`、`package.json`、`docs/v1-review.md`、`docs/v2-gap-and-changes.md`、`docs/design/md-reader.md`。历史草案只用来核对规格是否还在引用已被取代的说法。
本文件是独立评审，不修改上述规格。文中的改法是对下一份规格 PR 的建议。

对照的做法来自长期维护桌面 / Web 客户端的常见结构：功能垂直切片、端口与适配器、functional core / imperative shell、所有付费调用先预留再发送、契约测试锁住协议、Electron 安全清单、存储与协议可独立升级。不对照某一家内部代码。

---

## 0. 总评

**需要优化。** 不需要推倒重来。

这版基线已经把 v1 的主要教训写成了可执行的结构：按切片而不是按层分目录、依赖方向交给 dependency-cruiser、业务规则留在纯函数、seam 只过普通数据、引擎和供应商都在端口后面、Jev 的错误不算低分、密钥不进仓库、许可证是 Apache-2.0 并明确禁止 PyMuPDF。这些应该保持。

不能直接按本文字开始写 M1。有四件事会在第一批代码和 CI 里被焊死，之后再改要拆门禁或做数据迁移：

1. §7.1 的流水线在 §4.3 的依赖矩阵里没有合法的调用方。
2. 「整层搬进 utility 进程且代码不改」和 Electron 的进程能力矛盾。
3. API 优先之后，默认就要花钱的调用不在预算停机范围内，单价又是未知。
4. `oi-md/1` 表达不了「未核验公式必须显示裁图」。

下面 P0 在写切片和 CI 之前改规格。P1 在对应里程碑开工前改。P2 可以随实现补，不要为了它们推迟搭仓库。

## 1. 建议保持不动

这些已经对齐，后续规格 PR 不要为了「简化」删掉。

- 切片内部分层 `domain / application / adapters / ui`，切片之间只走 `index.ts`（ARCHITECTURE §3.1、§5.1）。
- core 不 import UI、DOM、路由、样式，包括 type-only；core 测试不渲染 UI（§2.1、G13、G14、G16）。这是防 `pdf/viewer.js` 的有效部分。
- seam 只传可结构化克隆的数据，错误是 `Result`，大对象走 `assetId`（§2.4）。
- 所有识别候选都要有 Jev 评估记录；`error` / `unavailable` 不算低分、不触发补救（PRD S5、AC-18；ARCHITECTURE §7.1、§7.3）。
- 有托管 API 时默认 API，「本地」是同一端口或同一种 worker 作业，两套来源跑同一份契约测试（§7.0、PRD AC-61 ②）。
- 本机与远程 worker 共用 `oi-parse/1`（HTTP + SSE）。要收紧的是谁持有第三方 Key，不是退回 stdio。
- 用户 Key 只进本机 `safeStorage`；开发 Key 只经 Cursor Secrets 注入到已登记的环境变量；仓库不读 `.env`（§8.3、§15.4；RULES N-05）。
- 项目许可证 Apache-2.0（`LICENSE` 版权人 wisdom-km，`package.json` 的 `license` 与 README 一致）。预处理用 pypdfium2，禁止 PyMuPDF，包括经 MiniCPM `pdf` extra 间接引入（Q6、RULES §1.5）。pypdfium2 传递依赖的许可证清单规格已留给 M1 的 G10，同意这个时机。
- v2 不迁移 v1 数据、不建 `writing` 目录、Markdown 只读并预留写入类型（Q5、Q8、D7）。
- 外发同意按服务商问一次，新增能力再追加告知。方向对，验收句子要改（见 P1-1）。

## 2. P0

写任何业务切片之前改掉。M1 若按现在的矩阵生成 dependency-cruiser，第一个真实功能就会违规，或者违规被写进装配根。

### P0-1 解析流水线没有归属切片

**证据**

- ARCHITECTURE §7.1 要求一条固定流水线：预处理，引擎 A / B、云 OCR、文字层、arXiv 源码，规范化，Jev，再按优先级链采用或补救，然后翻译。
- §4.3 的合法依赖里，没有任何切片同时看得到 `parsing`、`quality`、`formula`、`repair`、`translation`。
- `repair` 是唯一可以 import `quality` 的切片，而没有任何切片可以 import `repair`。`parsing` 没有入边。`library` 只依赖 `document`，`importPdf` 到不了 `submitParse`。
- 装配根可以看见全部 application（§5.1），但 F-02 禁止入口写业务分支，入口硬上限 150 行（§6）。
- §2.1 禁止把状态转移写进 UI。若 renderer 依次调用 `parsing`、`quality`、`document`、`translation`，流水线状态机就回到了 UI。

**为什么重要**

§14 写得很清楚：v1 的失败是「状态怎么判、译文从哪来、怎么显示」写在同一处，无法单测，也无法换一层。现在规则把每一层拆开了，却没有留下唯一允许编排它们的地方。M3 的人只会把分支写进 `composition-root.ts`，或者写进某个 UI hook。两种都会直接撞上已经设计好的门禁。

`formula-source` 同样没有入边。arXiv 对齐不会自己开始。

**改法**

增加一个没有界面的切片（建议名 `ingest`），只做编排：

- `domain/ingest-policy.ts`：把 §7.1 的分支写成纯函数。输入是候选、评估记录、预算与同意的结果；输出是下一步（采用、待评分、补救、停止）。不要在这里调用网络。
- `application/use-cases/open-document.ts`：一次用户动作。内部按顺序调用其他切片的 seam：入库、提交解析、取源码候选、评分、公式决定、必要时补救、采用、按块翻译。
- 依赖边只从 `ingest` 指出去：`library`、`parsing`、`document`、`quality`、`formula`、`formula-source`、`repair`、`translation`、`jobs` 的公开入口。同意、预算和供应商配置继续由装配根注入端口，`ingest` 不 import `settings`（保持 §4.3「业务切片不 import settings」）。其他切片不依赖 `ingest`。
- IPC 只有 `ingest.openDocument` 这一条用户入口。进度仍走 `jobs` 事件。
- 不要把编排放进 `jobs`。`jobs` 保持任务状态机。不要放进 `document`。`document` 现在不依赖任何切片，这个约束值得留。

M1 的 dependency-cruiser 按新图生成，并补一条 ADR。空的 `ingest` 切片和这条边属于 M1，不属于 M3。

### P0-2 不能把整个 application 搬进 utility 进程

**证据**

- ARCHITECTURE §1：application 与 adapters 默认在 main；M3 起若 main 卡顿，「整体迁到 Electron `utilityProcess`，代码不改，只改装配位置」。
- 同文 §4.5.2 已经写明：系统对话框和 `shell.openExternal` 只能在 `apps/desktop` 里，因为 Electron API 不能进 feature 包。
- §8.3 的密钥在 `safeStorage`。§9 的 `oi-asset://` 由 main 的协议处理器读文件。
- utility 进程是独立 Node 进程，不提供 `safeStorage`、`dialog`、`BrowserWindow`、`protocol`、`shell`。进程之间也不能共享对象，只能传可克隆的消息。

**为什么重要**

「代码不改」这句话会让 M1 把 SQLite、密钥和对话框装在同一个进程里，M3 再发现搬不走。届时要么放弃隔离，要么在热路径上临时拆进程。成熟的 Electron 应用在第一天就固定：崩溃和卡顿要隔离的是计算和数据库，系统能力留在 main。

§2.4 的普通数据 seam 其实已经够用来跨进程。缺的是承认这条边界，而不是以后「只改装配」。

**改法**

在 §1 改成固定职责，删掉「整体迁移、代码不改」：

- main：窗口、preload、IPC 发送方校验、`safeStorage`、对话框、`shell.openExternal`、`oi-asset://`、本机 worker 的拉起和关闭。
- utility（M3 按实测启用，不是一开始就禁止）：SQLite、出站 HTTP、`worker-client`、用例。启用时 main 只转发 seam 形状的请求和事件。
- 密钥明文只在 main 内存里出现，由 main 放进本机 worker 的请求头或桌面自己的 HTTPS 调用。utility 若要发供应商请求，只接收本次调用的临时授权，不接收可保存的 Key，也不写日志。
- M1 可以仍全部跑在 main，但目录和端口按上面的切分放置，使以后搬 utility 时搬的是「已通过端口注入的适配器」，不是一次重构。

### P0-3 默认付费路径不受预算停机约束

**证据**

- PRD §2、§4 原则 3：花钱可见、可控；受限预算到上限立即停。API 优先使 Jev 和引擎 B 成为默认路径，两者价格都未核实（`docs/v2-gap-and-changes.md` §7）。
- AC-06 只约束「付费补救请求」。
- ARCHITECTURE §7.3：预留只写了补救和翻译。预留失败进入 `waiting-budget`。
- AC-59 ③：Jev 的重试要先预留；首评没有同样的句子。AC-60 ⑥：引擎 B 按页记账，没有到顶即停。
- QM-10：单价未知时显示「未知」，不记为 0。金额账本无法把「未知」加到上限上，上限就永远到不了。
- `docs/architecture/README.md`「参数化决策」第 2 条曾经要求：没有可靠单价时用次数或 token 限额。现行规格没有接上这句话。

**为什么重要**

API 优先把「每次阅读都可能出网」变成默认。补救反而是后一步、默认还受开关约束。若预算只停补救，用户在受限档下仍会为 Jev 和文档解析持续付费，而界面上的金额是「未知」。这和原则 3、也和 AC-05「评分失败不要引发更多付费调用」的精神不一致：评分本身已经是付费调用。

**改法**

- 所有出网的模型调用在发送前经过同一个 `BudgetLedger.reserve`：Jev 首评与重试、引擎 B 文档解析、云 OCR、翻译、补救、问答、TTS、ASR。
- 单价已知时用金额。单价未知时用用户设置的次数或 token 上限，界面仍显示「未知」，不显示 0，也不把未知当成 0 去累加。
- 到顶之后，Jev 记 `unavailable`，原因 `budget`。随后走现成的「待评分、不补救、不改用别的服务商」。
- 在 AC-06 旁增加一条验收：未知单价 + 受限次数时，超出的 Jev 与文档解析请求数为 0。
- 翻译已经走预留（§7.3）。把 AC-06 的停止范围写成「全部已预留的付费调用」，避免测试只断言补救。

### P0-4 `oi-md/1` 表达不了未核验公式的裁图

**证据**

- PRD AC-04：未核验公式 100% 显示原页裁图。
- ARCHITECTURE §8.1.1：方言 `oi-md/1` 是 CommonMark + GFM 表格与删除线 + `$…$` / `$$…$$`，不含 HTML、wikilink、图片。
- 同节末尾把「`source-crop` 的行内公式在正文里怎么表示」标为待定，并指向差异清单 §6.2.1。差异清单写明：摘要可以先不算这个表示，但译文栏怎么画还要 Loom 与 Wisdom 定。

**为什么重要**

`formatVersion: 'oi-md/1'` 会进缓存键（§8.1.1）。M4 一旦按「正文里只有 LaTeX」落库，以后补上裁图就是方言升级，已翻译的块要整篇重算或做读时迁移。这是存储契约，不是界面细节。AC-04 又是硬门槛，不能留到翻译做完再发现方言写不下。

**改法**

在建立 `contracts/src/translation.ts` 之前定死，并写进规格正文，删掉「待定」：

- `oi-md/1` 继续不含图片和 HTML。
- 未核验公式不把 LaTeX 写进 `markdown` 去冒充已核验，也不在 Markdown 里发明图片语法。
- 片段表保存显示决定：`verified-latex` 或 `source-crop`，后者带 `assetId`。
- `getBlocks` 在 core 里生成 `MdDocument`：已核验公式是 math 节点，裁图是带 `assetId` 的公式节点。reader 只渲染这个文档。
- `formulaDigest` 继续覆盖显示决定和裁图内容哈希。这一条现有论证是对的，保留。

若产品坚持裁图必须出现在 Markdown 源字符串里，就定义唯一语法、契约测试和 `oi-md/1` 的版本说明。不要两种都留着。

## 3. P1

不阻塞「建立空仓库和门禁」，但阻塞对应功能的第一行业务代码。写进下一份规格，不要等实现时口头约定。

### P1-1 外发同意的验收句子和决定正文不一致

**证据**

- PRD §3.3 与 ARCHITECTURE §7.0 第 6 条：拒绝对话框时，列出的能力对该服务商请求为 0；追加告知被拒时，此前已同意的能力不受影响；不改用别的服务商。
- PRD AC-61 ④ 与 ⑦c 写成「对其他服务商的请求为 0」。
- 重新打开「外发前询问」之后要不要再问，两处都标「待 Wisdom 确认」（PRD §3.3、§9；ARCHITECTURE §7.0）。

**为什么重要**

按 ⑦c 的字面写测试，用户拒绝面壁之后，已经配置好的翻译服务也会被要求 0 次请求。这不是 19:30 的决定。测试比正文严，实现会跟着测试走。

**改法**

把 ④ 和 ⑦c 改成：本次被拒绝的能力，改发到其他服务商的次数为 0；其他服务商上已经同意的能力照常请求。

建议直接采纳规格里已经写明的补充，不必再悬着：重新打开开关后，没有在对话框里同意过的「服务商 + 能力」，下次使用前询问。这和「同意范围只覆盖列出过的能力」是同一条规则。

### P1-2 外发同意没有端口，「本地」基址可以是公网

**证据**

- §7.0 第 6 条：业务切片不 import `settings`，由装配根注入端口，在发请求前检查。
- §4.2 的 `settings` 端口只列出了 `secret-store`，没有同意端口。`egress-consent.ts` 只是 domain 文件。
- §7.0 表里「本地」是「本机 OpenAI 兼容服务」，没有要求基址是 loopback。用户可以把「本地」填成公网地址，从而不走「API」那一档的同意。

**为什么重要**

同意是跨切片规则。没有命名端口，翻译、问答、补救、worker 提交会各写一遍判断，开关语义会漂。基址不分类的话，设置项的名字就不能代表数据有没有离开机器。

**改法**

在 `contracts` 增加 `EgressCheck` 端口，由 `settings` 实现，`ingest` 和每个出站适配器在连接前调用。输入是服务商、能力、目的主机。目的主机不是 loopback、也不是用户明确标成「本机可信」的地址时，不论选项叫「本地」还是「API」，都走同一套按服务商同意。目的主机变了，视为新的服务商。

### P1-3 不要把用户的供应商 Key 交给远程 worker

**证据**

- ARCHITECTURE §1、§10.1：面壁 Key 放在每个 `evaluate` / `parse` 作业的 `OI-Provider-Authorization` 里。远程 worker 与本机 worker 一样接收。
- 翻译、问答、云 OCR 是桌面适配器直接 HTTPS，并不经 worker（§1 拓扑、§7.3）。
- worker 被要求不落盘、不进日志（§10.2，AC-59 ⑤）。远程进程、反向代理和用户自己的日志配置不在这个保证之内。

**为什么重要**

远程 worker 在「高级」里，是用户自己的机器，但那台机器不一定是阅读这台电脑。把面壁 Key 发过去，是为了让服务器再去调用面壁。桌面自己就能调用面壁。多一次跳转，Key 的信任面就扩大到整台服务器。本机 `127.0.0.1` 转发没有这个问题。

评分必须经 worker、映射必须经 `mapping.py`，这两条可以通过「本机 worker 转发、远程 worker 只做本机推理」同时满足，不必把 Key 送到远程。

**改法**

- 托管 API 由桌面或本机 worker 调用。本机 worker 可以继续转发，Key 只走 `127.0.0.1`，且不进 stdout、stderr、作业 JSON。
- 远程 worker 拒绝 `OI-Provider-Authorization`。它只使用那台服务器自己的配置。桌面不会为了「远程解析」把用户的面壁 Key 附在请求上。
- 契约测试：远程基址上出现该请求头则失败。本机回环地址上的现有 AC-59 ⑤ 保留。

### P1-4 决策记录里还留着已经被取代的句子

**证据**

- PRD §9 的 Q9：前半仍是「满足硬件推荐本机，8 GB 推荐远程；开发机按 CUDA 本机跑 Jev」。后半才是 18:44 的「默认 API，本地不要求」。同一条「已决定」里两种默认。
- `docs/v2-gap-and-changes.md` §6.3 写明引擎 B「由默认关改为默认」。同文 §7 的价格一行仍写「引擎 B 云端来源默认关」。
- 同文 §8 的落点表仍用 18:37 的「设置：本地 / 面壁 API」概括，没有标成已被 18:44 改名。

**为什么重要**

实现者会从决策记录的第一句抄默认值。Q9 的第一句和 AC-20、§7.4 推荐规则相反。差异清单 §7 是「未核实说法」的权威表，其中一行和产品默认相反，比正文里的历史说明更容易被当成现状。

**改法**

Q9 的「已决定」正文只保留 18:44 及之后仍然有效的规则。被取代的推荐算法移到该条末尾的「沿革」，并写明不要实现。§7 那一格改成「默认来源是 API；长期价格未核实」。§8 的旧措辞改成「本地 / API」。不要靠读者自己对时间戳。

### P1-5 阅读顺序有两套实现，没有对拍夹具

**证据**

- 文字层基础档的阅读顺序在 `parsing/domain/text-layer/`，TypeScript，无 Python 时也要工作（§4.2、Q2、AC-11）。
- 引擎 A 的 `ReadingOrderer` 在 Python `engines/reading_order/`（§7.2、§10.3）。
- §7.1：正式顺序由自写算法给出并版本化。V3 自带的顺序只作对照。
- PRD §7：v1 标注不是阅读顺序真值，QM-01 要另建基准。

**为什么重要**

阅读顺序是这个产品相对「把 PDF 交给一个端到端模型」的主要差异。两套规则会在基础档和引擎 A 上给出不同顺序，笔记锚点和译文块都挂在这个顺序上。M3 的 QM-01 基线会不知道测的是哪一套。

**改法**

M3 开工前定一条，并写进 §7.1：

- 推荐：worker 只返回区域、文字和坐标。顺序只在 TS `text-layer` 计算。基础档和引擎 A 调用同一组纯函数。Python 不保留第二套排序。
- 若排序必须留在 Python（测出 TS 在目标机器上过慢），把算法写成与语言无关的夹具，两侧输出必须一致。禁止两套「借鉴同一篇文档」的独立规则。

在决定之前，不要在 M1 同时生成两套空目录然后各自填逻辑。

### P1-6 借用多模态翻译没有放置位置

**证据**

- Q11、`settings/domain/translation-fallback.ts`：未配置翻译时可以借用多模态，默认关（§4.2）。
- §4.3：`translation` 不依赖 `repair`。`repair` 拥有 `MultimodalRepairProvider`。
- 没有任何句子说明借用时调用哪个端口。

**为什么重要**

M6 要么让 `translation` import `repair`，撞上矩阵；要么复制一个 OpenAI 客户端。两种都是规格没写清楚时的默认结局。

**改法**

翻译只依赖自己的 `TranslationProvider`。装配根在开关打开时，把同一个 OpenAI 兼容适配器同时注入翻译端口和补救端口。费用科目仍进多模态账本（AC-29）。这是装配期复用，不是编译期依赖。在 §4.3 用一句话写明，避免有人加一条 `translation → repair` 的边。

### P1-7 Markdown 有两条解析路径，和 IPC 体积冲突

**证据**

- §4.5.4：UI 不解析 Markdown。译文、笔记、问答由用例返回 `MdDocument`。
- §4.5.3：`pure.ts` 仍导出 `renderMarkdown` 给本切片 UI。`pure.ts` 可以打进 renderer（§2.4、§5.1）。
- §11：单条 IPC 默认超过 1 MB 就记 `ipc.oversize`。§4.5.6 允许单文件解析到 5 MB 的建议上限。
- AC-45：`features/markdown/src/ui` 与 `ui-kit` 不导入 Markdown 解析库。经 `pure.ts` 再导出 domain 解析器，传递依赖仍会进 renderer。

**为什么重要**

大文件会在「为了遵守 IPC 阈值而在 renderer 解析」和「为了遵守 AC-45 而把整棵 `MdDocument` 送过 IPC」之间摇摆。两条路径还会让安全策略（HTML 屏蔽、越界）有机会只在一侧生效。

**改法**

- renderer 不包含解析器。`renderMarkdown` 只供 `test/core` 和其他切片的 core 调用。
- G15 增加：renderer 与 `pure.ts` 的打进 UI 的那部分，传递上不可达 `domain/parse/`。
- 超过阈值的文档在 utility 解析，IPC 按块窗口返回（带 `src`），或返回解析缓存的 `assetId`。不要把 5 MB 文件的整棵 AST 当作一条 seam 消息。

`docs/design/md-reader.md` 正文 D2 仍写 `throwOnError:false`，并把 `MarkdownView` 放在切片 UI 里。文首入库说明和第 8 条已经改到规格。N-10 不许改正文。M2 只认 ARCHITECTURE §4.5.5 的那一份 `latex-policy`，不要按正文再写一份选项。

### P1-8 HTTP 错误映射会写在三个地方

**证据**

- 映射表在 ARCHITECTURE §7.4 的散文里。
- Python 计划有 `quality/http_errors.py`（§10.3）。
- TS 的规范化在 `quality/domain/evaluation-status.ts`（§7.3）。§7.3 又说 HTTP 失败按 §7.4 的表映射。

**为什么重要**

桌面和 worker 升级节奏不同。散文表格不能被 CI 比较。两边各实现一次，426 之外的行为会静默分叉，补救开关会在某一侧被错误触发。

**改法**

`contracts` 定义 worker 产物里的评估状态与 `detailCode`。Python 把 HTTP 状态映射成这个联合之后再出产物。TS 只规范化模型 verdict，不再解释 HTTP 状态码。`fixtures/protocol/` 用同一批样例在两侧断言。散文表改成该契约的说明，不再是第二份规范。

### P1-9 存储和协议还不能独立升级

**证据**

- §8.2 有按切片的 `migrations/` 和 `schema_migrations`。这是对的起点。
- 没有应用级 schema 世代、迁移失败时的回滚、旧应用打开新库时的行为。
- `oi-md/1` 只约束译文方言，不约束 `ContentBlock` / `AcceptedPageRevision` 的 JSON 世代。
- `oi-parse/1` 用 `OI-Protocol: 1` 和 HTTP 426（§10.2）。没有「同一主版本内只加可选字段」或「未知字段保留还是拒绝」。
- M8 才做安装包。用户数据从 M2 的 SQLite 开始积累。自动发版明确不做（PRD §3.2），手工升级仍然要能打开旧库。

**为什么重要**

切片迁移解决不了「桌面 1.3 打开 1.4 写过的库」和「新桌面连接用户半年前部署的远程 worker」。这两件事在第一次写表之后就会变成兼容包袱。

**改法**

用一篇短 ADR 写进规格，M2 建表之前合入：

- `oi.sqlite` 另有 `app_schema` 整数。应用只向前迁移。迁移前把数据库文件复制到 `staging/`。失败则停在旧文件上，不半迁移。
- 新应用遇到更高的 `app_schema`：只读打开或拒绝写入，并提示升级应用。不要静默改写。
- 文档 JSON 与协议消息：同一主版本内未知字段保留并回写；不兼容的变更升主版本。
- 桌面声明自己支持的 worker 协议范围。远程 worker 过旧时提示升级 worker，不把能力假装成可用。
- `oi-md` 的版本规则沿用 P0-4，不另起一套。

### P1-10 Electron 安全基线还缺会被 M2 打开的口子

**证据**

- §9 已有正确的底线：`contextIsolation`、`sandbox`、`nodeIntegration: false`、严格 CSP、禁止任意导航和 `window.open`、权限默认拒绝、`contextBridge` 不暴露 `ipcRenderer`、校验发送方 frame。
- CSP 没有具体指令。PDF.js 在实际集成时经常要求 wasm 或 eval。
- 没有 Electron fuses（例如禁止把应用当 Node 启动、只从 ASAR 加载）。
- `oi-asset://` 会读用户数据目录和笔记库图片（§9、§4.5.5）。自定义协议若注册成特权协议，renderer 里的页面可以借它读文件。二次 realpath 检查写了，注册方式和拒绝符号链接逃逸没有写成门禁。
- 差异清单 §7：本机 Windows 开发时 Cursor Secrets 如何注入环境变量仍是未核实。同时 N-05 禁止 `.env`。开发机就是 Windows。

**为什么重要**

M2 要开窗、要跑 PDF.js、要注册协议。没有事先写明的 CSP 和协议权限，会在打通 PDF 的那个 PR 里被放宽，之后没有测试再把它收紧。密钥方面，第一个在 Windows 上开发的人会在「规格不许读 `.env`」和「不知道变量从哪来」之间自己找一条路。

**改法**

- 在 §9 写上 CSP 初稿：`script-src 'self'`，`object-src 'none'`，禁止 `unsafe-eval`。若锁定的 PDF.js 证明必须放宽，单独 ADR 写最小例外和到期里程碑，不把例外写成默认。
- 打开 fuses：关闭 RunAsNode，只从 ASAR 加载应用，开启 cookie 加密。版本以 M1 锁定的 Electron 文档为准。
- `oi-asset` 不授予 renderer 通用文件能力。处理器只接受登记过的 `assetId`，再次确认真实路径仍在允许的根目录内，拒绝通过符号链接逃出该根。
- 开发 Key 的注入写清楚，仍然不写任何密钥值：云端 Agent 用 Cursor Secrets；本机只从 §15.4 已登记的环境变量读取，变量由操作系统凭据或当前会话注入。代码路径不增加 `.env` 读取。

### P1-11 门禁把「一个切片」和「一个 PR」焊反了

**证据**

- ARCHITECTURE §0：改一个功能只动一个切片；冲突面只剩契约和装配。
- RULES §2：一个 PR 只动一层或一个切片。
- RULES §8.1 第 2 条：改 UI 时默认不改 core。原文是「默认」。
- G17：同一个 PR 只要同时改 UI 路径和 core 路径就失败（§13）。M1 的退出条件要求这种 PR 被 CI 拒绝（PRD §8 M1）。
- RULES §3 与 G11：整个 `packages/contracts/**` 是热点，每个热点文件单 PR 不超过 30 行。

**为什么重要**

一个垂直切片的功能同时包含 domain 和 ui。G17 把一次可审查的改动拆成水平层，和 §0 的目标相反。契约文件加上请求、响应和错误码，很容易超过 30 行。M1 就会为了合入第一条 IPC 去申请 allowlist。豁免一多，行数门禁就回到 v1 那种「文档里写了、实际挡住的是守规则的人」。

G13–G16 没有这个问题。它们查的是依赖方向和测试是否穿过 seam，应该保留。

**改法**

- G17 改为：禁止同一个 PR 既改 UI，又改另一个切片的 core。同一切片的 UI 和 core 可以在一个 PR 里，前提是 seam 的类型变更已经单独合入。
- 热点收窄为装配根、`slots.ts`，以及被两个以上切片 import 的契约文件（如 `ids`、`errors`）。`contracts/src/ipc/<feature>.ts` 算该切片的文件，不套用 30 行。给契约 PR 一个单独的上限（建议 200 行非生成代码），超过才要求拆分理由。
- M1 的「故意违规样例」改成：core import React 类型、UI import 另一个切片的 application、core 测试渲染组件、UI PR 改了别的切片的 domain。不要再把「同一切片的 UI 和 core」当作必须失败的样例。

### P1-12 M6 承担了「公式变成已核验」的全部前提

**证据**

- PRD §8：M4 交付 arXiv 与翻译，源码候选在 M6 之前只标「待评分」，不显示为已核验。Jev、引擎 B、全路径评分、补救、预算、云 OCR、A/B 对比、Q11、高质量档都在 M6。
- 已核验的定义要求程序校验并且 Jev 有效且不低于阈值（PRD 术语「核验」；§7.5）。阈值本身还要等 QM-05 定标，而定标也在 M6。
- 引擎 A 的托管 API 在差异清单 §2.4.1：公开示例只取每页 Markdown，没有区域框。ARCHITECTURE §10.3 已经预留了 `aistudio_api.py`。

**为什么重要**

从 M3 到 M6 之前，阅读器只能显示裁图或待评分。这可以是有意的分期，但 M6 任何一个未核实项（价格、国内站、Windows 上的本地包、百度 API 的字段）都会挡住「公式已核验」这条主路径。目录里先放上 `aistudio_api.py`，会让人在核实失败之前把适配器写出来。

**改法**

- M3 的退出条件加上评分状态机和假评估器：采用版本里的每个识别候选都有 `EvaluationResult`，用录制样例，不调用真实 API。M6 只替换后端和做真机冒烟。
- 把现在的 M6 拆成可独立验收的三段：评分与预算、引擎 B、补救与云 OCR。高质量档仍等 QM-13，不要和评分端口绑在一起。
- 在核实「区域框、公式 LaTeX、版本锁定」之前，目录清单里不出现 `aistudio_api.py`。核实失败就从三条路径里删掉托管 API，不留空文件。

## 4. P2

不改变模块边界。写到对应里程碑的任务里即可。

### P2-1 函数 80 行和「深模块」互相拉

§2.2 引用 Ousterhout：不要为了行数把一个 seam 拆成一串浅函数。§6 仍规定函数硬上限 80 行、圈复杂度 15。`formula-policy` 和 `integrity-check` 是不变量集中的地方，按行数拆开会变难读。

改法：域规则按「一个不变量一个文件」拆。文件硬上限保留。函数上限继续约束适配器和 UI，对 domain 纯函数放宽到文件上限，并在评审清单里看职责数量，而不是再加一层豁免流程。

### P2-2 UI 事件总线能绕过依赖矩阵

§5.3 用 `contracts/src/ui-events.ts` 让 reader 发 `selection.changed`、notes 订阅。dependency-cruiser 看不见这条边。

改法：事件名登记在 §4.3 的旁注里。载荷只有普通数据，禁止回调和「请调用我」式的命令。新增事件和新增 import 边一样要 ADR。

### P2-3 历史草案的表格仍像现行需求

`docs/architecture/README.md` 文首已声明本目录是历史输入。下文「已确认的需求」仍列出手机派任务、账号同步、上传原 PDF、写作在 PDF 闭环后实现。根 README 写了冲突时以规格为准。Agent 经常读表格、不读文首。

改法：在该表上方加一句「本表已被 PRD §3.2、Q3、Q5、Q8 取代，不要当作 v2 范围」。不必改表内历史句子，也不必改草案 01/02/03 正文。

### P2-4 诊断包体积沿用 v1，装不下 API 优先之后的用量

§11 默认 7 天、2 MB，来自 v1。每次付费调用都要记 provider、模型和用量。2 MB 会把真正需要的错误码滚掉。崩溃不上传，这条保持。

改法：M2 做诊断页时把保留天数和体积改成设置项，默认提高到足以覆盖一次完整解析的用量事件。导出前仍走 `redaction-rules`。不要把正文写进日志。

### P2-5 CI 没有操作系统矩阵

§13 列出了 G1–G17，没有写跑在哪些系统上。开发机是 Windows。`safeStorage`、`fs.watch` 的原子替换、本机 worker 进程都和系统有关。差异清单 §7 已把这些标为未核实。

改法：M1 的 CI 在 Linux 上跑全部门禁；至少有一条 Windows 任务只做「无模型的 worker 健康检查和协议夹具」。macOS 签名留到 M8，由人执行，与现在的范围一致。

### P2-6 本机 worker 的监管状态机还没写

§10.1 有拉起、stdin 传一次性令牌、stdout 打印端口。没有崩溃重启上限、孤儿进程、单实例、握手失败后的状态。

改法：M3 写 supervisor 之前，在 §10 加一张小状态图：启动、就绪、退出、重启次数耗尽后的降级（文字层基础档）。逻辑放在 `worker-supervisor.ts` 一个文件里，不要塞进装配根。

### P2-7 服务商名单未定，OpenAI 兼容子集可以先定

翻译、多模态、问答的预置服务商名单规格已标待定（§7.0、§15.4）。端口形状已经有了。

改法：M4 前把一份最小的 chat completions 样例放进 `fixtures/protocol/`：消息、图片 content part、流式块、错误体。各家适配器只许在这份样例上有差异。名单仍可以按里程碑再填。

### P2-8 录制样例不要带上真实论文页

AC-59 要求去掉 `Authorization` 和图片内容。N-12 禁止把大 PDF 和权重提交进仓库。AC-10 诊断包不含正文。没有句子禁止契约夹具使用真实论文的裁图。

改法：协议夹具使用合成图和假令牌。需要真实页的基准放在不入库的语料流程里，仓库只存清单和 sha256（§3 的 `fixtures/corpus/` 已经是这个方向，保持）。

### P2-9 仓库现状和 M1 目标之间的落差是预期的

`package.json` 只有 `node --test`，没有 `packageManager`，也没有 workspace。`.nvmrc` 是 `20.19.2`，与 §15.1 一致。这是空仓库，不是规格错误。

改法：M1 当天引入 pnpm、Vitest 和 worker 的 uv。不要在 M0 再写一套「现在就用 npm 跑门禁」的说明。README 已指向规格，够用。

### P2-10 规格文件的写法在制造漂移

`ARCHITECTURE.md` 已超过 1300 行。2026-10-30 当天把 18:37、18:44、19:11、19:30 的决定追加进同一批章节。P1-4 就是这种追加的结果。

改法：不要现在拆文件。从下一次规格修改起，一个 PR 只改一个主题，并删掉被取代的句子，而不是在段尾再加「后来改为」。拆文件可以等 M1 的 ADR 目录建立之后再考虑。

## 6. 这些修改要几个 PR

**三个规格 PR，不要一个。** 也不要按「每个发现一个 PR」拆开。

PR #3 同一天把多条决定写进同一批段落，Q9 的前后半才会同时有效。再打一个触及流水线、安全、门禁和里程碑的大文档 PR，评审看不完，句子会再次叠在一起。

RULES §7 要求：一个决定改规格时，同 PR 更新所有受影响的规格。所以每个 PR 内部要同时改 `PRD.md`、`ARCHITECTURE.md` 和差异清单里对应的段落。跨 PR 的是主题，不是文件。

| 顺序 | 主题 | 包含 | 何时合入 |
| --- | --- | --- | --- |
