# Open Immerse v2 设计原则（design-principles）

状态：草案 v0.2（Loom，2026-10-30，Asia/Shanghai）；含 Wisdom 21:26 决定（标题栏合并、强调色跟随系统、设置为应用内页、3 套阅读主题、危险类示例）。
地位：v2 所有设计的**唯一原则来源**。[DESIGN.md](../DESIGN.md) 中的每一条规格都要能追溯到本文某条原则；冲突时以本文为准，本文与 PRD / ARCHITECTURE / RULES 冲突时以那三份为准（RULES 优先级）。
参考：Apple Human Interface Guidelines（https://developer.apple.com/design/ ，只借思想，不抄素材与原文）；Microsoft Windows 应用设计指南 / Fluent（https://learn.microsoft.com/windows/apps/design/ ）；WCAG 2.2（https://www.w3.org/TR/WCAG22/ ）。

## 1. 原则（7 条）

| # | 原则 | 一句话规则 | 为什么 | 怎么查 |
| --- | --- | --- | --- | --- |
| P1 | **内容优先（顺从）** | 阅读区里论文和译文占据视觉中心；界面控件用中性色、细线、无阴影，阅读时可以收起 | 用户来读论文，不是来看界面；Apple「deference」与 Windows「content first」一致 | 阅读主屏截图中，控件面积 ≤ 视口 15%（待审批）；阅读区内除状态标记外无强调色块 |
| P2 | **清晰** | 每个控件一个意思、一个名字；状态用文字说清，不只靠颜色或图标 | 公式「已核验 / 格式已核对 / 源码核对 / 未评分 / 待评分 / 原图 / 占位框」等状态用文字说清，直接影响信任。颜色、位置与图标待 Loom | 每个状态有可读文字；色盲模拟下仍可区分；同一概念全应用同一词 |
| P3 | **层级** | 每屏最多 1 个主按钮；按「主路径 / 支持 / 低频 / 危险」放置（§2） | 用户一眼知道下一步做什么 | 走查时数主按钮；低频项不出现在一级界面 |
| P4 | **遵循系统约定，优先原生控件** | 菜单、标题栏、对话框按钮顺序、快捷键、字体、强调色、滚动条都跟随当前系统（§3） | 用户在 Windows 和 macOS 上已有肌肉记忆；原生控件自带无障碍 | 对照 §3 表逐项核对；不自绘系统已有的控件（文件对话框、菜单、通知） |
| P5 | **不打断，就地反馈** | 结果在发生的位置显示（行内状态 + `role=status`）；只有需要用户**决定**的事才用模态对话框；不用 toast 报告失败 | 阅读时被弹窗打断代价高；PRD US-28 明确「不被弹窗打断」 | 失败/完成提示都在相关元素旁；模态对话框清单只含「需要决定」的场景 |
| P6 | **人人可用** | 满足 §4 无障碍基线 | 法规与道德要求；也让键盘重度用户（研究者）更快 | §4 每条都有自动或手动检查 |
| P7 | **界面只表达，规则在 core** | UI 规格只描述「显示什么、怎么交互」；何时显示、能否操作、状态如何转移都由 core 经 seam 返回的数据决定 | ARCHITECTURE §2.1、RULES §8（Wisdom 原文约束） | 每个屏的规格里，条件都写成「当 seam 返回 X 时显示 Y」，不出现由 UI 计算的业务条件 |

## 2. 功能分类与放置

| 类别 | 定义 | 放置规则 |
| --- | --- | --- |
| **主路径** | 大多数用户每次都做的事（打开 PDF、读、对照跳转、选中写笔记、提问） | 一级界面直接可见；有快捷键；最多 1 个主按钮 |
| **支持** | 经常但不总是用（字号、主题、重译单块、切换栏位、搜索） | 工具栏图标或面板，悬停/聚焦显示；也在菜单中 |
| **低频** | 偶尔设置一次（服务商、Key、预算、诊断、高级远程 worker） | 放「设置」或「⋯」菜单；不占阅读界面 |
| **危险** | 会花钱、外发数据、降低保护（如关闭外发前询问）、撤回同意、删除数据、不可撤销 | 必须明确确认（对话框写清后果，默认焦点在安全选项，如外发同意框默认「不允许」）；不放在主按钮位置；按钮用动词说清后果（「删除笔记」而非「确定」） |

## 3. 平台约定（Windows / macOS）

| 主题 | macOS | Windows | 规则 |
| --- | --- | --- | --- |
| 菜单 | 屏幕顶部系统菜单栏，「应用名」菜单含「设置…」⌘, | 标题栏内菜单按钮；「文件 › 设置」Ctrl+, | 用 Electron 原生 `Menu`；两平台的「设置」都打开**应用内设置页**，不开新窗口（Wisdom 21:26） |
| 标题栏 | 红绿灯在左，与工具栏合并（`hiddenInset`） | 系统按钮在右（`titleBarOverlay`），保留 Snap Layouts | 标题栏与工具栏合并（Wisdom 2026-10-30 21:26）；保留系统窗口按钮的原生行为 |
| 对话框按钮顺序 | 取消在左，主操作在**最右** | 主操作在**左**（OK/取消），取消在右 | 组件 `DialogActions` 按平台排序，代码中只声明「主 / 次 / 取消」角色 |
| 修饰键 | ⌘（Command）、⌥ | Ctrl、Alt | 快捷键定义一次，显示时按平台换符号；`Mod` = ⌘/Ctrl |
| 字体 | SF（`-apple-system` / `system-ui`）、中文 PingFang SC | Segoe UI Variable / Segoe UI，中文 Microsoft YaHei UI | 字体栈 `system-ui` 起头，不打包界面字体 |
| 强调色 | 系统强调色（`systemPreferences.getAccentColor` / CSS `AccentColor`） | 同左 | 应用外壳**全部**跟随系统强调色（含主按钮），前景色计算到 ≥ 4.5:1，取不到才回落品牌色；阅读区不跟随（Wisdom 21:26） |
| 焦点 | 焦点环（蓝色外发光，跟随强调色） | 双色焦点框（黑 + 白，2px），高对比可见 | 统一用 `:focus-visible` 2px 实线 + 2px 偏移；Windows 高对比时用系统色 |
| 高对比 | 「增强对比度」「减少透明度」 | 对比度主题（High Contrast） | 支持 `prefers-contrast: more` 与 `forced-colors: active`；强制色下不靠背景色传达状态 |
| 滚动条 | 叠加式，滚动时出现 | 细滚动条，悬停加宽 | 用系统滚动条，不自绘 |
| 文件打开 | ⌘O；拖到 Dock 图标 | Ctrl+O；拖到窗口 | 都支持拖入窗口 |
| 关闭最后一个窗口 | 应用保持运行 | 应用退出 | 按平台默认 |

## 4. 无障碍基线（WCAG 2.2 AA）

1. **对比度**：正文与小字 ≥ 4.5:1；大字（≥ 18.66px 粗体或 ≥ 24px）≥ 3:1；控件边框、焦点指示、图标 ≥ 3:1（WCAG 1.4.3、1.4.11）。每个颜色 token 在 DESIGN 中标出对比度。
2. **键盘**：所有功能可只用键盘完成；Tab 顺序与视觉顺序一致；模态对话框内焦点循环，Esc 关闭并把焦点还给触发元素；不设键盘陷阱。
3. **焦点可见**：只用 `:focus-visible` 显示焦点，不得全局 `outline:none`；焦点指示 ≥ 2px、对比 ≥ 3:1，且不被遮挡（WCAG 2.4.7、2.4.11）。
4. **减少动效**：`prefers-reduced-motion: reduce` 时，所有位移/缩放动画改为 ≤ 100ms 的淡入或直接切换；不自动滚动动画（跳转改为瞬时定位）。
5. **读屏标签**：图标按钮都有 `aria-label`；状态变化用 `role=status`（礼貌播报），错误需要立即处理时才用 `role=alert`；公式提供 LaTeX 文本作可访问名称（KaTeX 的 MathML 输出）；裁图公式 `alt` 为「公式图片，LaTeX 候选：…」或「公式图片，未识别」。
6. **缩放**：界面放大到 200% 不丢内容、不出现双向滚动（阅读区除外）。
7. **目标尺寸**：可点击目标 ≥ 24×24px（WCAG 2.5.8）；工具栏图标按钮建议 28–32px（待审批）。

## 5. 浅色 / 深色

- 默认**跟随系统**（`nativeTheme.themeSource = 'system'`）；设置中可选「跟随系统 / 浅色 / 深色」。
- 每个颜色 token 必须同时给出浅色与深色值，并分别达到 §4 第 1 条。不允许只在一种模式下测对比度。
- 阅读区主题（`--oi-reader-*`）与应用主题分开，固定 3 套：白、暖纸、深色（Wisdom 21:26）；阅读区不跟随系统强调色，但「深色」阅读主题在系统深色时为默认。
- 深色不是反色：图片、PDF 原文页面保持原样，不做颜色反转（可选「暗化 PDF 页面」为低频项，v2 不做）。

## 6. 走查分级

每次设计走查或 UI PR 评审，问题按三级记录：

| 级别 | 判定 | 处理 |
| --- | --- | --- |
| **必须改** | 违反 §4 无障碍基线、违反 P7（UI 里出现业务规则）、危险操作无确认、信息丢失或误导（如把「待评分」显示成「低分」）、平台约定反向（按钮顺序、快捷键错） | 合入前修复 |
| **可延后** | 违反 P1–P5 但不误导（多余主按钮、间距不齐、文案啰嗦、低频项位置不佳） | 登记，随下个里程碑修 |
| **不改** | 个人偏好、与本文无关的视觉口味、平台间本就该不同的差异 | 记录理由后关闭 |
