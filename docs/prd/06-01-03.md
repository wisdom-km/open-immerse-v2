#### 6.1.3 面壁开放平台（Q9 补充，AC-59–AC-60）

来自 Wisdom 2026-10-30 18:37 的决定（§3.3）。契约测试用本机假服务与录制样例，不调用真实服务、不花钱；调用真实服务的冒烟只在环境变量 `MODELBEST_API_KEY` 存在时运行，不是 CI 门禁（ARCHITECTURE §12）。

| 编号 | 标准 | 对应 |
| --- | --- | --- |
| AC-59 | 面壁 Jev API（契约测试）：① 请求固定 `model: "MiniCPM-OCR-Jev"`、`stream: false`、`minicpm_ocr_jev.mode: "score"`；每个请求的 `items` ≤ 64（65 项拆成 64 + 1）；`messages` 非空，图片都是 `data:image/png;base64,` 形式；② `choices[0].message.content` 再解析一次，`results[i]` 对应 `items[i]`，verdict 按 ARCHITECTURE §7.3 规范化；`content` 解析失败的整批记 `error/service_failed`；③ HTTP 错误先映射为 `ProviderFailure`，再按 ARCHITECTURE §7.4「面壁 API」表处理（TS 与 Python 两侧用同一批样例）：400 / 404 / 422 记 `error/invalid_request`、重试 0 次；401 / 403 / 402 整批记 `unavailable`（原因 `auth` / `quota`）、重试 0 次、设置入口出现提示；413 拆半重试；429 与 5xx 退避重试且次数有上限；每次重试都从作业的额度信封里扣一次请求，信封用完后上游请求为 0（ARCHITECTURE §7.8）；④ 没填 Key，或「外发前询问」开着且没同意数据外发时，对面壁的请求为 0，结果为 `unavailable`（「待评分」），补救请求为 0（AC-05）；开关关着时按 AC-61 ⑦f，没同意也照常请求；⑤ Key 原文只出现在两处请求头里（桌面端到本机 worker 的 `OI-Provider-Authorization`，只经回环地址；worker 到面壁的 `Authorization`），发往远程 worker 的请求中出现 0 次（AC-65）；worker 作业 JSON、SSE 事件、产物、日志、诊断包、录制样例与仓库（gitleaks）中命中 0 次，renderer 只收到「已设置 / 未设置」（AC-09、DESIGN DS-17）；⑥ 响应的 `usage` 100% 记入预算账本，未填单价时费用显示「未知」、不记为 0；⑦ `evaluatorVersion` 含部署方式 `modelbest-api`、模型名与站点，换站点即产生新的 `evaluatorVersion`，旧结果 0 条被改写 | US-19, US-29；M6a |
