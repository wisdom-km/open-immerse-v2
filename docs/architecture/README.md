## 核心需求已对齐，以下是实施时的参数化决策

1. Jev 按 text/formula/table 分类的有效评分阈值，以及公式来源检查规则：以代表性论文样本定标。
2. 用户自行设置预算金额；没有可靠厂商价格信息时提供调用次数/token 限额与估算状态，不承诺虚假的精确金额控制。
3. 临时文件 TTL、回收站周期、原录音保存和音频离线缓存：按产品设置与后续同步阶段确定。
4. 新仓 Node/模型运行时版本、安装包签名与测试设备：在 P0 固定，并建立双平台验证矩阵。

这些问题不能由旧文档中的历史决定替用户回答；用户本次明确提出的双引擎和桌面方向优先于旧计划。

## 建议的架构方向（尚非源码实现）

- TypeScript 领域与应用层负责文献库、翻译、来源校验、任务编排和语音用例，桌面与未来云端 Node 服务复用。
- Python worker 负责 PDF 预处理、Paddle、MiniCPM 和 Jev；不同模型运行时可以分进程/环境，避免依赖冲突。
- 桌面通过受控 IPC 调用本地应用层；远程模型服务通过版本化协议接入。未来手机通过带账号鉴权的云 API 调用同一组用例。
- 数据以版本化结构模型为权威，Markdown/LaTeX 是输出视图；原 PDF、识别候选、采用结果和翻译分开保存。
- 桌面 SQLite + 文件；未来云端 PostgreSQL + 对象存储。首版采用模块化服务，按真实负载再拆分部署。
- 账号同步、任务执行、设备在线与语音会话是不同协议；一个解析 HTTP 接口不能自动提供跨设备续接。

## 后续仍需细化的产品条件

- 手机具体 UI 与离线批注深度在手机里程碑细化；核心协议已保留引用与同步能力。
- 每篇/每区域的预算、重试上限与调用用量换算随供应方适配和基准结果配置。
- 代表性 PDF 类型、公式与表格验收优先级、首屏与整篇处理的速度/费用目标。
- 语音讲解语言、公式朗读方式、音频与原文定位方式，以及原始录音保存策略。
- 云服务目标用户、部署地域、是否提供自托管部署包，以及开发周期与维护人力。
- 临时资产、采用后的结构化结果和原始音频分别设置保留时间；不能用一个全局清理任务删除有效文献库文件。

## 十五项提问及确认轨迹

1. 运行模式：本地/远程混合。
2. 平台：首版 Windows 与 macOS；手机未来 iPhone 与 Android。
3. 互通能力：同账号数据与对话接续，手机发起解析任务。
4. 桌面技术栈：Electron + TypeScript + React，Python 独立推理。
5. 典型硬件：8 GB、核显/M1 的轻客户端目标，重计算可远程。
6. 语音阶段：先朗读/讲解与语音笔记，实时语音后置。
7. 首版云范围：远程解析可用；账号同步与手机任务先合同后上线。
8. 模型费用：自有 API / 自建服务先行，官方收费云后续。
9. 数据边界：按论文同步原件及结构化产物，密钥不随同步。
10. 公式不确定：候选保留，多模态复核仍失败则原图。
11. 仓库边界：仅 open-immerse-v2 实施，旧仓完全不动。
12. 产品范围：聚焦 PDF 核心、问答、基础语音及可扩展模块。
13. 写作范围：核心之后做带引用草稿与导出，编辑器编译后置。
14. 补救费用策略：用户开关与预算选择，超限回原图。
15. 手机执行：可直接远程，服务或预算不足则等待。
